# 018. Outgoing webhooks sign with a per-center secret kept encrypted

- Status: accepted
- Date: 2026-10-13

## Context and problem statement

Training centers are told about their applications, contracts, disbursements and arrears by
webhook. A center must be able to tell that a delivery comes from Tramo and was not replayed or
altered, and Tramo must keep posting through an endpoint that is down for a while, without
posting the same event twice as two different deliveries. The URL is chosen by the center, so the
worker posts to an address someone outside Tramo controls. How are deliveries authenticated, how
is the signing key kept, and what stops a URL from pointing the worker at Tramo's own network?

## Decision drivers

- The center verifies with something it holds; Tramo signs with the same thing (HMAC) or with a
  private key the center trusts (asymmetric).
- A key that leaks from Tramo's database lets anyone forge deliveries to that center.
- Tramo already verifies the webhooks it receives as `t=<unix>,v1=<HMAC-SHA256 of "t.body">` with a
  five-minute window (e-signature, payment provider): one scheme to document and test.
- Retries and redeliveries must be distinguishable from new events on the center's side.

## Considered options

1. HMAC-SHA256 with a per-center secret generated by Tramo, stored hashed.
2. HMAC-SHA256 with a per-center secret generated by Tramo, stored encrypted (ADR 014).
3. Asymmetric signatures (Ed25519) with one Tramo key pair and a published public key.

## Decision outcome

Option 2. Configuring the webhook (`PUT /centers/:id/webhook`) generates a 256-bit secret
(`whsec_` prefix), returns it once and stores it encrypted with the field cipher, bound to its
row. Each attempt posts the event as JSON with `X-Tramo-Signature: t=<unix>,v1=<hex>` over
`"<t>.<body>"`, `X-Tramo-Delivery-Id` and `X-Tramo-Event`; the body's `id` is the Tramo event id,
the same in every attempt and redelivery, so the center deduplicates by it. Configuring again
rotates the secret.

Option 1 cannot sign: an HMAC needs the secret itself, and a hash of it is not enough (the plan's
first sketch said "hashed", which only works for secrets Tramo verifies, like API keys). Option 3
needs no secret per center and nothing to leak per center, but asks every center to handle key
rotation and a less common verification, and differs from the incoming scheme.

Deliveries are written down in the same transaction as the event that caused them is consumed
(one per center and event, a unique index), and a job posts each: five attempts per round with
exponential backoff from `WEBHOOK_RETRY_DELAY_MS`, then the delivery is `failed`, its job goes to
the dead-letter queue, and the center or ops redeliver it as a new round. A 2xx is a delivery;
anything else, a timeout or a redirect (never followed) is a failed attempt.

### Consequences

- Good: the center verifies with the same few lines it would write for any common provider, and
  a replayed request is refused after five minutes.
- Good: a secret read from a database dump is useless without the field encryption key.
- Bad: the worker holds the decrypted secret while posting; a compromised worker can forge
  deliveries. It can also do everything else Tramo does, so it is not a new exposure.
- Bad: the URL is the center's choice. Where `WEBHOOK_PRIVATE_TARGETS_ENABLED` is off (always
  in production: it refuses to start with it on) only https to public addresses is posted: the
  connection resolves the host itself and refuses it if any address is loopback, private,
  link-local (cloud metadata), carrier-grade NAT, documentation, multicast, reserved, or an IPv6
  form carrying an IPv4 address (NAT64, 6to4, Teredo); the address checked is the one connected
  to, so a name that changes its answer (DNS rebinding) cannot slip in between. Redirects are
  not followed, the answer's body is never read (only its status), and a center sees a category
  of failure (`timeout`, `connection_failed`, `http_503`), never the error text, so the
  webhook is not a probe of Tramo's network. An egress proxy would add a second line.
- Bad: a center learns of an event only after its round of attempts; one whose endpoint is down
  for hours sees the delivery `failed` and has to redeliver (`POST
/centers/:id/webhook-deliveries/:deliveryId/redeliver`).

### Rotation overlap (2026-10-13)

Rotating the secret used to switch signatures at once: every delivery between the `PUT` and the
center deploying the new secret failed its verification. The secret a rotation replaces is now
kept for 24 hours (`SECRET_ROTATION_OVERLAP_MS`), encrypted and bound to its row like the current
one (`previous_secret_encrypted`, with `previous_secret_expires_at`), and each delivery made in
that window carries one `v1` per secret, the current one first:
`X-Tramo-Signature: t=<unix>,v1=<hex with the new secret>,v1=<hex with the old one>`. Receivers
must accept a request when any `v1` matches a secret they hold, as Tramo does for the callbacks it
receives. Only the secret just replaced overlaps: rotating twice within a day drops the oldest.
A removed webhook configured again starts with its new secret alone. After the window the
replaced secret stays stored, unused, until the next rotation overwrites it.
